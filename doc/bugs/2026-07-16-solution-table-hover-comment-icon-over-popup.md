# Solution: suppress and self-heal the hover overlay around open cell popups

**Fixed:** 2026-07-16

## What changed

All in `components/database/table-view.tsx` (`SortableTableRow`):

- **Set-time guard.** The cell's `onMouseEnter` already skipped setting `hoveredCell` for the exact cell being edited; broadened the condition to `!editPop` (any popup open anywhere in the table), not just a match on this row/property.
- **Render-time guard.** The hover overlay's portal mount is now gated on `hoveredCell && !editPop`, not just `hoveredCell` — a second, independent check so it doesn't matter *how* `hoveredCell` ended up truthy, the overlay simply cannot render while a popup is open.
- **Commit-phase clear.** Added a `useEffect` that clears `hoveredCell` whenever `editPop` becomes set for this row, mirroring the existing pattern just above it that does the same for `activeCell` — this runs after React commits, independent of event-handler timing.
- **Self-healing on stale hover.** The existing scroll-driven cleanup effect now also listens for `mousemove` and clears `hoveredCell` if the real cursor position has drifted outside the snapshotted cell `rect` — this is what actually fixes the "stuck" overlay, since it no longer depends on a `mouseleave` event firing at all.
- **Popup z-index.** The main `CellEditorPopover` mount (`editPop`-driven) now passes `zIndex={300}`, matching the override this file already uses in three other `CellEditorPopover` mounts to sit above `CellActionOverlay`'s `zIndex: 200`.
- **Popup got stuck in a broken visual state after deleting the last file.** `FileEditor`'s `showAddForm` flag (`components/database/cells/cell-editor.tsx`) — which toggled between the full "Add a file or image" Upload/Link tabs UI and a compact "+ Add" row once a file existed — was only ever computed once at mount (`useState(files.length === 0)`), so deleting the last file emptied the list but left the popup showing the compact row from when a file still existed. Per further direction, the fix isn't "revert to the full tabs UI" — it's that the compact "+ Add a file or image" row is now the *only* empty-state appearance, always: `showAddForm` now simply defaults to `false` (no file-count-dependent initial value, no effect needed to correct it later), so a brand-new never-touched cell and a just-emptied one look identical, and there's no in-between broken state to get stuck in.
- **Global, caller-independent popup-open flag.** `CellEditorInner` (`components/database/cells/cell-editor.tsx`) now sets a ref-counted `document.body.dataset.cellPopupOpen` flag while mounted (any popup type, any view), and `CellActionOverlay` (`components/database/cell-action-overlay.tsx`) checks it and self-suppresses if set — independent of whatever hover-state bookkeeping the calling view does or doesn't do. This is a second, wholly independent layer on top of table-view.tsx's own `!editPop` guards, in case the overlap is ever triggered from a code path this fix's other changes don't cover.

## Why this fixes the root cause

The stuck-overlay symptom was caused by relying on `mouseleave` as the *only* way to clear hover state — a real gap, since leave events aren't guaranteed to fire for every way a cursor stops being "over" an element. The `mousemove`-based self-heal validates against the actual cursor position on every move, so it recovers regardless of which specific event got skipped. The `!editPop` guards (set-time and render-time) independently ensure that even a *correctly*-set hover state never renders while a popup is open, closing the second gap where a different nearby cell's legitimate hover could still overlap an open popup. The two fixes are complementary — either alone leaves a gap the other closes.

The `showAddForm` fix removes the underlying condition entirely rather than patching around it: with only one possible empty-state appearance, there's no code path left that can produce a wrong-sized or wrong-shaped popup after a delete. The global `document.body` flag exists because per-view local state (`editPop`) requires every view that shows a similar hover affordance to correctly thread that state through — a `document.body`-level flag set by the popup itself, checked directly inside `CellActionOverlay`, works regardless of which view opened the popup or whether that view's own hover logic was wired up correctly.

## Verification

`tsc --noEmit` passes for all touched files. Live-verified via an automated browser session (authenticated through a server-generated magic link) that the popup opens/closes correctly and the hover-suppression code paths are reachable; a fully conclusive live re-test of the exact reported overlap was not achieved in this session — one repro screenshot showed the "Gantt" tab visually active while what was actually rendered still matched table view's popup markup (Upload/Link tabs, not the plain `<table>` Gantt's own file lacks entirely), suggesting a transient tab-switch rendering state rather than a Gantt-specific gap, but this wasn't conclusively isolated. The global `document.body` flag was added specifically so the fix doesn't depend on correctly identifying which view was responsible. Worth a manual spot-check across every view that shows this popup (table, Gantt property list, entry side panel, entry properties panel): attach a file, delete it, confirm the popup always shows the same compact "+ Add a file or image" row, and that no other row/cell's hover comment or copy icon ever renders on top of an open popup.
